01 Overview

The research at a glance

The research run is complete. Every figure below is computed in the browser from the final pipeline output: every app researched, every record schema-checked, and accuracy measured on a separately built ground-truth sample.

What is investigated for every application

  1. AuthenticationWhich auth schemes the official docs describe — OAuth2, API key, token, basic.
  2. Credential accessWhether a developer can self-serve credentials or needs approval, a paid plan or a partnership.
  3. API surfaceWhether a documented public API exists, and its type (REST, GraphQL…).
  4. MCP availabilityOfficial, community or no MCP server found in the official MCP Registry.
  5. BuildabilityA verdict on whether an agent toolkit can realistically be built, and the main blocker.

    07 Recommendations & Limitations

    What remains difficult

    Priorities computed from adjudicated rows, followed by the honest limits of this method.

    Limitations

    01Only part of the dataset has ground truth

    Ground truth covers a seeded sample only. The remaining apps carry Groq-generated findings with no independent check, so treat their values with the measured error rate in mind. The ground truth itself was prepared with LLM assistance and has not yet been re-checked by a person.

    02Groq underperformed the crawler on MCP

    The deep crawler queries the official MCP Registry directly; Groq sometimes classified vendor-owned MCP servers as third-party/community or unclear. The registry itself is young, so "None found" is not "none exists". Treat MCP counts as indicative.

    03Composio was tested separately

    The Groq → Composio tool path was demonstrated in a dedicated round-trip test. It was not used to investigate the 100 apps: in the research run Groq only re-read pages the crawler had already fetched. Composio's catalog served as secondary evidence.

    04Model comparison is not statistically fair

    The fallback model only took over when the primary model hit its free daily token cap, so the two models adjudicated different apps with different category mixes, and only a handful of sample apps each. The gap does not show which model is more accurate.

    05Apps without evidence links

    Where no official API documentation was found, the record says so explicitly (insufficient evidence, unclear access) instead of citing something weak. Those apps carry no Groq citation; any link shown comes from the reviewer's check.

    06Documentation quality & discoverability

    Auth and access details are scattered across API references, help centres and pricing pages; some vendors render docs only with JavaScript.

    07Authentication ambiguity

    "API key", "personal access token" and "bearer token" are often the same thing under different names, so auth is scored as coarse classes.

    08Gated developer access

    Credential access lives in partner and pricing pages, not API references — it is the hardest field to settle.

    09Incomplete or conflicting evidence

    Where official pages disagree or are silent, the field stays Unclear or the app is marked Insufficient evidence — never upgraded to a positive claim.

    10LLM hallucination risk

    Every Groq citation is checked against the pages actually fetched; uncited or unfetched claims are dropped or flagged, not trusted. Rejected generations failed the schema check and were retried, never saved.
